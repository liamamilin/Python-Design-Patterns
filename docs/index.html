01 · 怎么读这本书

从“能工作”到“能改变”

以「数据与数据的处理」作为思考锚点：程序要表示数据、处理数据。需求变化时，困难往往不在某个运算本身，而在创建方式、变化位置、调用关系、对象协作、状态和处理步骤如何组织。设计模式是针对其中某些反复出现的困难总结出的可选方案。

第一步

写朴素 Python

数据是什么？计算发生在哪里？先用最简单的写法解决当前问题。

第二步

加一个真实新要求

哪些部分不得不跟着修改？指出具体代码，而不是空说“扩展性差”。

第三步

判断是否值得

修改成本真的值得改变组织方式吗？设计模式是一个选项，不是奖章。

第四步

三方比较

直接写法、经典模式、Python 简化写法，用可运行行为和适用边界做出选择。

如果第二步没有出现真正的困难，就停在第一步。不强行使用模式。

贯穿全书的五个诊断问题

读任何一章、看任何一段代码时都可以拿出来问一遍。第 3 题是全书的重心。

  1. Q1被表示的现实对象、事件或规则是什么？代码用什么数据表示它们？
  2. Q2哪些操作对这些数据产生结果？操作会修改什么、输出什么？
  3. Q3什么可能变化？什么不应随之改变？
  4. Q4当前最简单的方案在哪里遇到困难？有证据，还是假设？
  5. Q5新方案把变化集中到了哪里？引入了什么额外成本？

「数据与处理」是思考的起点，不是说所有程序问题都能还原成两个标签。阅读时还要留意时间、状态、副作用、外部系统、错误处理、性能、并发，以及团队之间的协作。

先分清五个层次

“设计模式”常被和别的东西混为一谈。本书只把第三层叫作设计模式，其他几层会在需要时单独讲。

读者需要什么

能读懂变量、条件判断、循环、函数与最基本的类即可，不要求学过软件架构或 UML。每一章尽量能独立阅读；必须用到的新概念，先用普通语言解释，再引入术语。

读完之后，你应该能够

  • 说清一段代码表示了什么数据、谁负责处理、哪些地方会变化
  • 用最简单的 Python 实现原始需求
  • 通过可观察的新需求定位真实困难（重复修改、多处分支、接口不兼容），而不是凭空宣布“耦合高”
  • 对照困难选择模式或更简洁的 Python 替代，并说明代价
  • 为选择写小测试，知道何时撤回不必要的抽象

04 · 推导示例

为什么会需要“工厂”？

先看一个缩短的例子，感受本书怎样讲一个模式：同一个发送通知的小工具经历四个阶段，需求每变一次，先问“现在的写法还好用吗”。目的不是证明工厂方法胜过简单函数，而是看清什么时候才轮到它。完整内容见第 05 章。

后面的代码沿用前面定义的类。把四段代码按顺序放进同一个文件，就能运行出每段下方的结果。

  1. 1

    只有邮件一种方式

    数据是消息正文和发送方式，处理是选择发送者并生成消息。示例只返回文字，不发送真实邮件。

    好代码，没有升级的理由 
    class EmailSender:
    def send(self, message: str) -> str:
        return f"Email: {message}"


sender = EmailSender()
print(sender.send("订单已发货"))
    输出Email: 订单已发货
  2. 2

    新增短信：直接判断

    只有一个入口、两种方式时，几行 if 判断清楚直接。不要因为出现了两行判断就引入设计模式。

    依然是好代码 
    class SmsSender:
    def send(self, message: str) -> str:
        return f"SMS: {message}"


def notify(channel: str, message: str) -> str:
    if channel == "email":
        sender = EmailSender()
    elif channel == "sms":
        sender = SmsSender()
    else:
        raise ValueError(f"未知渠道: {channel}")
    return sender.send(message)
    输出notify("sms", "订单已发货") → SMS: 订单已发货
  3. 3

    同样的判断出现在多处

    “发送每日报告”也写了一套相同的判断。加第三种渠道时要改好几处，还可能漏改。真正的问题是创建哪种发送者的决定分散在多处，而不是 if 本身。最朴素的解法是把创建逻辑集中起来。

    简单工厂函数，不是 GoF 工厂方法 
    def make_sender(channel: str):
    senders = {"email": EmailSender, "sms": SmsSender}
    try:
        sender_type = senders[channel]
    except KeyError:
        raise ValueError(f"未知渠道: {channel}") from None
    return sender_type()


def notify(channel: str, message: str) -> str:
    return make_sender(channel).send(message)
    输出make_sender("fax") → ValueError: 未知渠道: fax
  4. 4

    创建决定随任务类型而变

    “交易通知”默认用邮件，“紧急通知”默认用短信；这些任务共享同一工作流程。父类固定流程并留出创建入口，由子类决定实例化哪种发送者，这才是 GoF 工厂方法的核心。

    GoF 工厂方法 · 第 05 章 
    from abc import ABC, abstractmethod


class NotificationJob(ABC):
    def run(self, message: str) -> str:
        sender = self.create_sender()
        return sender.send(message)

    @abstractmethod
    def create_sender(self):
        """由不同类型的任务决定使用哪种发送者。"""


class TransactionJob(NotificationJob):
    def create_sender(self):
        return EmailSender()


class UrgentJob(NotificationJob):
    def create_sender(self):
        return SmsSender()
    输出TransactionJob().run("订单已发货") → Email: 订单已发货 UrgentJob().run("系统告警") → SMS: 系统告警

    角色：产品是具备 send 能力的发送者；创建者 NotificationJob 定义流程与 create_sender 入口；具体创建者 TransactionJob、UrgentJob 决定实例化哪一种。

如果只有两个场景，任务之间的步骤也没有真正的差异，抽象基类加两个子类反而比两行判断更费解。不需要父类固定流程、不需要子类定制创建行为时，保留简单工厂函数更合适。

模式存在，不代表当前必须采用。先看问题有没有发生，再看模式能否用合理的成本解决问题。

05 · 每个模式章

每一章你会读到什么

每个模式章都会讲清下面八件事。顺序和篇幅因模式而异，但“为什么需要它”和“什么时候不该用它”（高亮的两项）每章都有。

1眼前的任务

一个具体的小场景：谁要做什么，输入和输出是什么。

2不用模式的写法

最简单的可运行 Python，它已经能解决当前问题。

3需求变了

新增一条真实要求，指出原写法具体要改哪几处代码。

4新的组织方式

谁负责什么发生了哪些调整；必要时配一张数据流或关系图。

5代码与验证

完整可运行的例子，带测试，覆盖原需求和变化后的需求。

6代价与边界

多出来的类、间接层和测试成本，以及一个不该用这个模式的小问题。

7Python 还能怎么写

函数、数据类、内置协议或标准库能否更简洁？更简洁就直接用。

8练习

换一个新情境，由你判断用还是不用；给出思路，不给唯一答案。

每章末尾还有一段简短小结。

06 · 易混点

这些地方本书会特别讲清

每个模式先讲 GoF 的经典意图，再讲 Python 中可以怎样变形。下面是最容易被讲混的几处，读到对应章节时可以留意。

●工厂

根据参数返回对象的“简单工厂”函数很常用，但它不是 GoF 23 种模式之一。工厂方法的关键是由子类决定创建哪种对象。

●单例

“只有一个实例”在同一进程、多线程、多进程下含义不同。书中会比较共享实例、模块级对象和直接传入依赖这几种做法的取舍。

●装饰器

GoF 装饰器是层层包装对象来叠加职责；Python 的 @ 语法可以体现类似思想，但用了 @ 不等于用了这个模式。

●享元

只有大量对象重复保存同类数据时才值得用；书中会尽量用能实际测量的对象数量或内存差异说明效果，而不是空谈性能。

●观察者

通知顺序、某个接收者出错时怎么办、何时取消订阅，都需要事先约定；几十行的示例不是可靠的事件系统。

●命令

撤销、重试和“重复执行结果不变”是三件不同的事；已经发出去的邮件、扣过的款，不一定能撤回。

●迭代器

Python 已经内建迭代协议，iter()、next() 和生成器能解决大部分需求，通常不必手写一套 GoF 风格的类。

●解释器

只处理受控的、极小的规则语言；任何时候都不要用 eval 执行不可信的输入。

编程范式 ≠ 设计模式 架构模式 ≠ GoF 设计模式 语言语法 ≠ 设计模式 用了模式 ≠ 一定更好

书中示例以 Python 3.11+ 为目标，优先使用标准库，不需要网络或 API 密钥；每个模式章至少有一个可运行的示例和配套测试。
