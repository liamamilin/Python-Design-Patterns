第五部分 · 回到 Python

第 31 章　简单代码与模式代码的取舍

本章要回答：面对同一个需求，一个直白的函数和一套“灵活”的结构，怎样比较？比较的依据是什么，而不是什么？

前面的每一章都在问“什么时候不该用”。这一章把这些零散的判断收拢起来：用一个小例子，把两种写法放在一起，从可读性、变化的位置、状态、副作用、测试和团队维护几个角度逐一比较。目的不是得出“简单永远更好”或“模式永远更好”，而是练习怎样比较。

眼前的任务#

第 01 章的练习里说过：积分规则变得很多、而且经常增减时，才值得把它们单独组织起来。现在，一家连锁咖啡店的积分规则是这样的：

  • 每消费 1 元得 1 分；
  • 周三积分翻倍；
  • 金卡会员积分 1.5 倍；
  • 生日当月每笔订单额外送 100 分，不参与倍数。

写法一：一个函数#

def points_simple(o: Order) -> int:
    points = o.amount // 100  # 每消费 1 元得 1 分
    if o.day.weekday() == 2:
        points *= 2  # 周三双倍
    if o.tier == "金卡":
        points = points * 3 // 2  # 金卡 1.5 倍
    if o.day.month == o.birthday_month:
        points += 100  # 生日月额外送 100 分，不参与倍数
    return points

写法二：一组规则#

每条规则是一个函数，接收当前积分和订单，返回调整后的积分（第 17 章的策略、第 28 章的函数写法）：

def wednesday_double(points: int, o: Order) -> int:
    return points * 2 if o.day.weekday() == 2 else points


def gold_card(points: int, o: Order) -> int:
    return points * 3 // 2 if o.tier == "金卡" else points


def birthday_bonus(points: int, o: Order) -> int:
    return points + 100 if o.day.month == o.birthday_month else points


RULES: list[Rule] = [wednesday_double, gold_card, birthday_bonus]


def points_rules(o: Order, rules: list[Rule] = RULES) -> int:
    points = o.amount // 100
    for rule in rules:
        points = rule(points, o)
    return points

对四个有代表性的订单，两种写法给出完全相同的积分（测试 test_both_versions_agree）。功能上没有区别。区别在别处。

逐项比较#

可读性#

读写法一，从上到下十行，规则的全貌和它们之间的关系一目了然：先翻倍，再乘 1.5，最后加生日分。注释里那句“不参与倍数”，正是靠代码的先后顺序来实现的。

读写法二，要先看 points_rules 的循环，再分别看三个规则函数，最后看 RULES 列表的顺序，才能拼出同样的全貌。每条规则单独看更清楚，整体反而要多跳几处。

判断依据：读者需要理解的是“每一条规则”，还是“所有规则合起来的结果”？

变化的位置#

假设要加一条“新会员首单送 50 分”。

  • 写法一：在函数里加一个 if，找到合适的位置。
  • 写法二：写一个新函数，加进列表（测试 test_adding_a_rule_is_one_line_in_the_list）。

假设要在某次活动期间临时关掉“周三双倍”。

  • 写法一：加一个开关参数，或者临时改代码，活动结束后再改回来。
  • 写法二：传一个不含这条规则的列表即可，不需要改任何已有代码（测试 test_turning_a_rule_off）。

判断依据：规则是偶尔由程序员修改，还是经常按活动、按门店、按时间段组合？如果是后者，写法二的“规则是数据”就很有价值，规则列表甚至可以从配置中读取。

隐藏的依赖：顺序#

写法二有一个写法一没有的风险。规则之间存在顺序依赖：“生日分不参与倍数”要求 birthday_bonus 排在两条倍数规则之后。在写法一里，这个顺序就是代码本身，一眼可见；在写法二里，它变成了一个列表中元素的排列，而列表看起来像是“可以随意调整的配置”。

如果有人觉得“生日优惠比较重要，放在最前面”，把列表改成 [birthday_bonus, gold_card, wednesday_double]，同一笔订单的积分从 484 变成了 684，没有任何错误提示。测试 test_rule_order_changes_the_result 穷举了三条规则的六种排列，得到了四种不同的积分。

这是“灵活”的典型代价：结构变得可以自由组合之后，组合本身就成了一个可能出错的地方。 解决办法有几种：在列表旁边写清楚顺序约束，并用测试固定；把规则分成“倍数类”和“加分类”两组，结构上保证加分在最后；或者干脆承认规则之间的关系比较紧，回到写法一。

判断依据：规则之间是互相独立，还是彼此有先后、有交互？越独立，越适合拆开；越纠缠，越适合写在一起。

状态和副作用#

两种写法都是纯计算：输入订单，输出积分，不修改任何东西，不依赖当前时间（日期是订单的一部分）。在这个维度上它们没有差别，也都很容易测试。

如果规则开始依赖外部状态，比如“本月已经送过生日分的会员不再送”，就需要查询历史记录。这时写法一的函数会多出一个参数或者一次数据库查询；写法二的规则函数签名要扩展，所有规则都要跟着改。副作用和外部状态的出现，往往比规则数量的增加更能改变设计的选择。

测试#

两种写法都容易测试。差别在于测试的粒度：写法二可以单独测试每一条规则，也可以测试任意规则组合；写法一只能通过构造不同的订单，间接覆盖每一个分支。规则很多、组合复杂时，写法二的测试更有针对性。

团队维护#

谁会修改积分规则？

  • 如果是同一个开发者，偶尔调整：写法一更直接，改一处，看一处。
  • 如果是多个团队分别负责不同的活动规则，或者运营人员通过后台配置：写法二让每条规则可以独立开发、独立上线，也更容易对接配置界面（更进一步，就是第 27 章的规则语言）。

汇总#

维度写法一：一个函数写法二：一组规则本例的判断依据
可读性全貌和关系一眼可见单条规则清楚，全貌要拼读者关心整体还是单条
增加规则改函数加函数、加一项差不多
按场合组合、开关规则要加参数或改代码换一个列表即可组合是否频繁
规则间的顺序写在代码里，显式藏在列表顺序里，容易被误改规则是否互相独立
测试按订单间接覆盖可以单测每条规则和组合规则多少、组合多少
团队协作适合一个人维护适合多人、多团队、配置化谁在改，多频繁

对本例当前的需求（四条规则，由一个开发者维护，很少变化，规则之间有顺序关系），写法一更合适。如果下个季度市场部门要求“每个门店可以自己选择参加哪些活动”，结论就会改变。

几个不该用的比较依据#

  • “这样更面向对象”或“这是设计模式”。 名字不是理由。要说出它解决了哪个具体的困难。
  • “以后可能会需要”。 为想象中的需求付出现在的复杂度，往往不划算。等变化真的出现时再重构，那时你也更清楚变化的方向（第 04 章的检查清单里也有这一条）。
  • 代码行数。 写法二多几行，不说明它更差；写法一更短，也不说明它更好。要看的是理解和修改它需要付出的代价。
  • “别人都这么写”。 别人的项目有别人的变化方向。

小结#

  • 比较两种写法，不看名字和行数，看它们在可读性、变化的位置、规则之间的关系、状态与副作用、测试粒度和团队协作上的差异。
  • “灵活”的结构会引入新的出错方式，比如顺序依赖被藏进了配置；越灵活，越需要测试和说明来约束组合。
  • 规则互相独立、需要频繁组合、由多人维护时，把它们拆开更好；规则之间关系紧密、由一人维护、很少变化时，写在一起更好。
  • 结论取决于当前的需求。需求变了，结论可以变；重构的前提是有测试保证行为不变。

练习#

市场部提出三个新需求：

  1. 每个门店可以自己决定参加哪些积分活动；
  2. 新增“雨天积分加倍”，需要查询当天的天气；
  3. 积分规则的修改要有记录，出了问题能查到“某天某笔订单是按哪些规则算的”。

对每一个需求，分别回答：它更有利于写法一还是写法二？为什么？三个需求加在一起之后，你会怎样设计？

思路提示：需求 1 是“按场合组合规则”，明显有利于写法二：每个门店有自己的规则列表，可以存在配置里。需求 2 引入了外部数据（天气），两种写法都要把天气作为输入传进来（不要让规则函数自己去查网络，参见第 01 章把外部输入推到最外层的做法）；写法二需要给所有规则函数加一个参数，或者把天气放进订单数据。需求 3 有利于写法二：每条规则有名字，计算时可以把“依次应用了哪些规则、每一步的积分”记录下来，写法一很难做到这一点。三个需求加在一起，写法二的收益已经超过了它的代价，但要同时解决顺序依赖的问题，比如把规则分成“倍数”和“加分”两个阶段。这正是“需求变了，结论也会变”的例子。
