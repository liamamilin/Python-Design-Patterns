# 第 01 章　从数据与处理理解程序

> 本章要回答：真实需求如何变成可以表达的数据与操作？“输入 → 处理 → 结果”什么时候不足以描述状态和副作用？

在谈任何设计之前，我们先练一个基本功：看到一个需求，能说出程序里**有哪些数据**、**谁在处理它们**。后面所有章节讨论的“变化”和“组织”，都建立在这个基本功上。

## 一张小票

街角的咖啡店想让收银程序打印小票。一位顾客点了两杯拿铁、一个可颂。小票上要有每样东西的小计和总价。

先别急着写代码。这个场景里，现实中的东西是“订单”：它由几行组成，每行有商品名、单价和数量。用 Python 最直接的表示是一个列表，列表里每一项是一个字典：

```python
# 数据：一张订单由若干行组成，每行记录商品名、单价（单位：分）和数量
order = [
    {"name": "拿铁", "price": 2800, "qty": 2},
    {"name": "可颂", "price": 1500, "qty": 1},
]
```

注意单价写的是 `2800`，单位是**分**，不是 `28.0` 元。原因很现实：计算机里的小数大多不能精确表示，`0.1 + 0.2` 在 Python 里并不等于 `0.3`。收银程序算错一分钱也是错，所以金额用整数“分”来存，只在显示时换算成元。这是一个关于“数据怎么表示”的决定，它会影响后面所有的处理。

## 处理：从输入得到结果

有了数据，第一个处理是算总价：

```python
def order_total(lines: list[dict]) -> int:
    """处理：输入订单，输出总价（分）。不修改订单，也不依赖外部状态。"""
    return sum(line["price"] * line["qty"] for line in lines)


def format_yuan(cents: int) -> str:
    return f"¥{cents / 100:.2f}"
```

`order_total(order)` 得到 `7100`，`format_yuan(7100)` 得到 `"¥71.00"`。

这两个函数有一个很好的性质：**只看输入，只给输出**。同样的订单传进去，无论调用多少次、在什么时候调用，结果都一样；它们也不会偷偷修改传进来的列表。这类函数最容易理解，也最容易测试，只要比较输入和输出即可。

这就是最朴素的程序模型：

```text
输入（订单） → 处理（求和、格式化） → 结果（¥71.00）
```

很多小程序到这里就足够了。但只要再往前走一步，这个模型就开始不够用。

## 当“输入 → 处理 → 结果”不够用

### 状态：结果取决于过去

咖啡店推出会员卡：每消费满 10 元积 1 分，积分会累计。

```python
class MemberCard:
    """会员卡记住累计积分：同样的调用，结果取决于之前发生过什么。"""

    def __init__(self) -> None:
        self.points = 0

    def add_purchase(self, cents: int) -> int:
        earned = cents // 1000  # 每满 10 元积 1 分
        self.points += earned
        return self.points
```

同一张卡，用同样的金额 `7100` 调用两次 `add_purchase`，第一次返回 `7`，第二次返回 `14`。输入完全一样，结果却不同，因为卡**记住了**之前发生的事。这份被记住的数据叫作**状态**。

有状态并不是坏事，会员积分本来就需要累计。但它改变了我们读代码的方式：要知道一次调用的结果，不能只看参数，还要知道对象此刻处于什么状态、之前被谁改过。后面讲到状态模式（[第 20 章](../part-04/20-state.md)）、备忘录（[第 25 章](../part-04/25-memento.md)）时，我们处理的都是这类问题。

### 副作用与时间：程序碰到了外部世界

小票最终要打印出来，上面还要印下单时间：

```python
def print_receipt(lines: list[dict], now: datetime, out: TextIO) -> None:
    """副作用：把小票写到 out。时间和输出位置都由调用方传入。"""
    out.write(f"时间：{now:%Y-%m-%d %H:%M}\n")
    for line in lines:
        subtotal = line["price"] * line["qty"]
        out.write(f"{line['name']} x{line['qty']}  {format_yuan(subtotal)}\n")
    out.write(f"合计：{format_yuan(order_total(lines))}\n")
```

这个函数不返回任何结果，它的全部意义在于**对外部世界产生影响**：往屏幕、文件或打印机写字。这种影响叫作**副作用**。“当前时间”也是来自外部的数据，每次运行都不一样。

这里有一个小小的设计选择：时间 `now` 和输出位置 `out` 都由调用方传进来，而不是在函数里直接调用 `datetime.now()`、直接 `print`。好处在测试时最明显：测试可以传入一个固定时间和一个内存里的 `io.StringIO`，然后逐字检查打印内容。如果函数自己去取当前时间、自己打印到屏幕，测试就很难写。

> 把“会变的外部因素”变成参数，是一个比任何设计模式都更基础、也更常用的手法。后面你会反复看到它。

## 换一种数据表示

用字典表示订单行很方便，但有一个隐患：如果某处把 `"price"` 拼成了 `"prcie"`，程序直到真正去读这个键时才会报 `KeyError`，可能已经离写错的地方很远了。

Python 的 `dataclass` 可以把“一行订单长什么样”写成明确的结构：

```python
@dataclass(frozen=True)
class OrderLine:
    name: str
    price: int  # 单位：分
    qty: int

    @property
    def subtotal(self) -> int:
        return self.price * self.qty


def total_of(lines: list[OrderLine]) -> int:
    return sum(line.subtotal for line in lines)
```

现在字段名写错会在创建对象时立刻报错；`frozen=True` 让订单行创建后不能被修改，读代码的人不用担心它在别处被悄悄改掉。“小计”这个计算也挪到了数据旁边。

这是不是比字典“更好”？不一定。字典适合快速试验、数据来自 JSON 的场合；`dataclass` 适合结构稳定、会在很多地方传递的数据。**数据的表示方式本身就是设计的一部分**，它决定了哪些错误能早点被发现、哪些操作写起来顺手。[第 03 章](03-python-building-blocks.md)会更系统地比较这些工具。

## 用五个问题读这段代码

全书反复使用五个诊断问题。拿小票程序试一遍：

1. **被表示的现实对象是什么？用什么数据表示？** 订单和订单行；用字典列表或 `OrderLine` 列表，金额用整数分。
2. **哪些操作产生结果？会修改什么、输出什么？** `order_total` 只计算不修改；`MemberCard.add_purchase` 修改积分；`print_receipt` 向外输出。
3. **什么可能变化？什么不应随之改变？** 小票格式、积分规则可能变；总价的算法不应该因为换了打印格式而改变。
4. **最简单的方案在哪里遇到困难？有证据吗？** 目前没有。这几段代码都短小清楚，没有理由引入任何模式。
5. **新方案把变化集中到了哪里？** 还不需要新方案。

第 4 个问题的答案很重要：**看出了数据和处理，不等于要马上加抽象**。现在的代码就是好代码。

## 这和设计模式有什么关系

设计模式讨论的是：当需求变化时，数据、处理、状态和副作用应该怎样组织，才不至于每次改动都牵一发而动全身。如果连“这段代码里有什么数据、谁在处理、哪里有状态、哪里碰到外部世界”都说不清，就没法判断变化会落在哪里，也就谈不上选择模式。

所以本书把“数据与处理”当作出发点。但它只是起点：真实程序还要面对时间、状态、副作用、外部系统、错误、性能和并发。我们会在具体章节里逐一遇到它们，而不是假装两个标签能解释一切。

## 小结

- 先识别数据：现实中的东西用什么结构表示，单位和精度怎么定。
- 再识别处理：哪些操作只是从输入算出结果，哪些会修改状态，哪些会碰到外部世界。
- 只看输入、只给输出的函数最容易理解和测试；有状态和副作用时，要额外知道“之前发生过什么”和“外部发生了什么”。
- 把时间、输出位置这类外部因素变成参数，是最基础的设计手法。
- 看清结构之后，如果没有出现真实困难，就保持简单。

## 练习

咖啡店想加一条规则：周三会员消费积分翻倍。

1. 这条规则涉及哪些数据？“今天是不是周三”从哪里来？
2. 你会把“是否周三”放进 `MemberCard` 里自己判断，还是作为参数传给 `add_purchase`？两种写法分别怎样测试？
3. 这个改动需要引入新的类或设计模式吗？

**思路提示**：如果让 `MemberCard` 自己调用 `datetime.now()`，测试就得等到周三，或者想办法伪造系统时间；把日期或倍率作为参数传入，测试只需要多传一个值。对这样一条规则，一个参数就够了，不需要任何模式。只有当积分规则变得很多、而且经常增减时，才值得考虑把“积分规则”单独组织起来（参见[第 17 章](../part-04/17-strategy.md)“策略”）。
