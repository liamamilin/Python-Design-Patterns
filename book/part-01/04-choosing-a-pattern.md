# 第 04 章　从问题选择模式

> 本章要回答：范式、设计模式、架构和惯用写法有什么不同？怎样根据变化和代价，而不是根据名称，来选择方案？

前三章一直在说“先看清问题”。这一章把方法收拢起来：设计模式到底是什么，它和其他常被混在一起的概念有什么区别，以及面对一个具体变化时，怎样在“直接写法、经典模式、Python 的简化写法”之间做选择。

## 先分清几个层次

“设计模式”这个词经常被用得很宽：有人把面向对象叫作模式，有人把微服务叫作模式，也有人把 Python 的装饰器语法叫作模式。为了后面讨论不走样，本书把它们分成五个层次：

| 层次 | 典型例子 | 是什么 |
|---|---|---|
| 基本表达 | 数字、变量、判断、循环、函数、类 | 编程语言允许我们写什么 |
| 编程范式 | 命令式、过程式、面向对象、函数式 | 程序采用什么组织与表达方式 |
| 设计模式 | GoF 工厂方法、策略、代理等 | 针对反复出现的设计困难的方案 |
| Python 惯用法 | 直接传函数、迭代协议、装饰器语法 | Python 语言特性支持的简洁写法 |
| 更大范围的设计 | 分层、消息队列、分布式部署等 | 系统级组织问题，本书只在必要处提及 |

几个容易混淆的地方：

- **面向对象是范式，不是模式。** 它是一种组织程序的整体方式；设计模式是在这种方式里，针对某个具体困难的一种做法。
- **Python 的 `@decorator` 是语法，不是 GoF 装饰器模式。** 两者有相似的思想（在不改动原有代码的情况下叠加行为），但用了 `@` 不代表采用了 GoF 装饰器，GoF 装饰器也不必用 `@` 来写。第 13 章和第 30 章会详细区分。
- **“工厂”在 Python 社区常泛指任何“返回对象的函数”。** 这种简单工厂函数很常用，但它不是 GoF 23 种模式之一。GoF 的工厂方法有更具体的含义（[第 05 章](../part-02/05-factory-method.md)）。
- **架构关心的是整个系统怎样分块、怎样部署。** 本书讲的设计模式发生在函数、类和对象之间，范围小得多。

## GoF 是什么

本书说的 23 种设计模式，来自 1994 年出版的《设计模式：可复用面向对象软件的基础》（*Design Patterns: Elements of Reusable Object-Oriented Software*）。四位作者 Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides 常被称为“四人帮”（Gang of Four），所以这套模式也叫 GoF 模式。

这本书的贡献是给一批反复出现的设计做法起了名字，并说明了每种做法的意图、适用情境、参与者和后果。有了共同的名字，开发者之间讨论设计就方便了。

但要记住它诞生的背景：书中示例主要使用 C++ 和 Smalltalk。在那样的语言里，函数不能像普通数据一样随手传递，很多事情只能靠类和继承来完成。Python 里函数就是对象，还有迭代协议、装饰器语法、`dataclass` 等工具，**有些模式在 Python 里会变得非常简单，有些甚至已经内建在语言里了**。本书对每个模式都会先忠实讲清它的经典意图，再说明在 Python 里可以怎样写得更轻。

GoF 按用途把 23 种模式分成三类：

| 类别 | 关心的问题 | 模式（本书章号） |
|---|---|---|
| 创建型（5 种） | 对象怎样被创建，创建的决定放在哪里 | 工厂方法 05、抽象工厂 06、建造者 07、原型 08、单例 09 |
| 结构型（7 种） | 类和对象怎样组合成更大的结构 | 适配器 10、桥接 11、组合 12、装饰器 13、外观 14、享元 15、代理 16 |
| 行为型（11 种） | 对象之间怎样分配职责、怎样协作 | 策略 17、观察者 18、命令 19、状态 20、模板方法 21、责任链 22、迭代器 23、中介者 24、备忘录 25、访问者 26、解释器 27 |

每种模式的意图可以用一句话概括。这张表适合在读完对应章节后回来查，而不是现在背下来：

| 模式 | 一句话意图 |
|---|---|
| 工厂方法 | 定义一个创建对象的接口，让子类决定实例化哪一个类 |
| 抽象工厂 | 提供一个接口，用来创建一系列相关或相互依赖的对象，而不指定它们的具体类 |
| 建造者 | 把复杂对象的构建过程与它的表示分离，同样的构建过程可以得到不同的表示 |
| 原型 | 用一个现成的实例作为原型，通过复制它来创建新对象 |
| 单例 | 保证一个类只有一个实例，并提供访问它的全局入口 |
| 适配器 | 把一个类的接口转换成调用方期望的另一个接口 |
| 桥接 | 把抽象部分与实现部分分开，使两者可以独立变化 |
| 组合 | 把对象组织成树形的“部分—整体”结构，让调用方统一对待单个对象和组合对象 |
| 装饰器 | 动态地给一个对象叠加额外的职责 |
| 外观 | 为子系统中的一组接口提供一个统一、易用的入口 |
| 享元 | 通过共享来高效地支持大量细粒度的对象 |
| 代理 | 为另一个对象提供一个替身，以控制对它的访问 |
| 策略 | 定义一系列算法，把它们分别封装起来，使它们可以互相替换 |
| 观察者 | 定义一对多的依赖，当一个对象的状态改变时，所有依赖它的对象都得到通知 |
| 命令 | 把一个请求封装成对象，从而可以排队、记录、撤销请求 |
| 状态 | 让对象在内部状态改变时改变自己的行为 |
| 模板方法 | 在一个操作里定义算法的骨架，把其中某些步骤留给子类实现 |
| 责任链 | 让多个对象都有机会处理请求，把它们连成一条链，请求沿链传递直到被处理 |
| 迭代器 | 提供一种方法，顺序访问集合中的元素，而不暴露集合的内部表示 |
| 中介者 | 用一个中介对象封装一组对象之间的交互，使它们不必互相直接引用 |
| 备忘录 | 在不破坏封装的前提下，保存对象的内部状态，以便以后恢复 |
| 访问者 | 在不修改元素类的前提下，为一个对象结构中的元素定义新的操作 |
| 解释器 | 为一种简单语言定义文法的表示，并用它来解释这种语言中的句子 |

## 用变化来选择，而不是用名称

初学者最常见的选择方式是：“我在学策略模式，这里有一堆 `if`，那就用策略吧。”这样选出来的方案，常常比原来的代码更难读。

本书建议反过来：**先说清楚变化是什么，再看哪些方案能把这个变化放到一个合适的位置，最后比较代价。**

下面用一个具体例子走一遍。

### 停车场收费

停车场按车型收费：小汽车每小时 5 元，摩托车每小时 2 元，不足一小时按一小时算。

```python
def billable_hours(minutes: int) -> int:
    """不足一小时按一小时算，最少收一小时。"""
    return max(1, math.ceil(minutes / 60))
```

最直接的写法是条件判断：

```python
def fee_by_if(vehicle: str, minutes: int) -> int:
    hours = billable_hours(minutes)
    if vehicle == "car":
        return 5 * hours
    if vehicle == "motorcycle":
        return 2 * hours
    raise ValueError(f"未知车型: {vehicle}")
```

停 90 分钟的小汽车收 10 元，停 30 分钟的摩托车收 2 元。

现在来了一个新需求：**货车每小时 10 元，最低收 20 元。**

### 第一步：说清变化是什么

变化的是“某种车型怎样根据时长算钱”。这是一条**规则**，而且是一段**行为**：货车的规则不只是换一个单价，还多了“最低 20 元”。计费小时数的算法不变，调用收费的地方也不变。

### 第二步：看有没有证据

如果车型只有两三种，而且一年才变一次，那么在 `if` 里加一个分支就是最好的方案，改动小、一眼能看懂。

但假设停车场运营方告诉我们：每个分店有自己的特殊车型（大巴、新能源车、残障车位），而且这些规则由各分店的开发者自己维护，他们不应该去改总部的收费函数。这就是一个明确的、可观察的变化来源：**规则的种类会持续增加，而且增加规则的人不是写收费函数的人。**

### 第三步：列出候选方案

**写法一：继续加 `if`。** 每加一种车型，就要修改 `fee_by_if`。分店的开发者必须改总部的代码。

**写法二：字典里放函数。**

```python
RATES = {
    "car": lambda hours: 5 * hours,
    "motorcycle": lambda hours: 2 * hours,
}


def fee_by_table(vehicle: str, minutes: int) -> int:
    try:
        rule = RATES[vehicle]
    except KeyError:
        raise ValueError(f"未知车型: {vehicle}") from None
    return rule(billable_hours(minutes))
```

新增货车只要定义一个函数，再往字典里注册一行，`fee_by_table` 一个字都不用改：

```python
def truck_fee(hours: int) -> int:
    return max(20, 10 * hours)
```

分店的代码里写 `RATES["truck"] = truck_fee` 即可。停 61 分钟的货车算 2 小时，收 20 元；停 3 小时收 30 元。

**写法三：每种规则一个类。** 这就是第 17 章要讲的策略模式的经典形式：

```python
class FeeRule(ABC):
    @abstractmethod
    def fee(self, hours: int) -> int:
        """根据计费小时数返回费用（元）。"""


class CarRule(FeeRule):
    def fee(self, hours: int) -> int:
        return 5 * hours


class MotorcycleRule(FeeRule):
    def fee(self, hours: int) -> int:
        return 2 * hours


def fee_by_rule(rule: FeeRule, minutes: int) -> int:
    return rule.fee(billable_hours(minutes))
```

但请注意，调用方手里拿到的仍然是 `"car"` 这样的字符串。要把字符串变成规则对象，还得有一张表：

```python
RULES = {"car": CarRule(), "motorcycle": MotorcycleRule()}
```

**选择并没有因为用了类而消失，只是换了一个位置。** 这是很多人引入策略模式后才发现的事。

### 第四步：比较代价

三种写法的行为完全一样（[测试](../../tests/test_ch04_parking.py)逐一验证了这一点），区别在于：

| | `if` 判断 | 字典里放函数 | 每种规则一个类 |
|---|---|---|---|
| 新增货车要改哪里 | 修改 `fee_by_if` | 新写一个函数，注册一行 | 新写一个类，注册一行 |
| 分店能否不改总部代码 | 不能 | 能 | 能 |
| 读代码时一眼看全部规则 | 最容易 | 较容易 | 要翻好几个类 |
| 一条规则需要多个操作（算费用、生成说明、月卡折扣） | 每个操作一串 `if` | 字典里要放好几个函数，开始别扭 | 很自然：一个类里放几个方法 |
| 额外的概念和代码 | 无 | 很少 | 抽象基类、多个子类 |

据此可以做出判断：

- 如果规则少、变化少：**用 `if`**，不要犹豫。
- 如果规则会持续增加、由别人维护，而每条规则只是“一个计算”：**用字典里放函数**。在 Python 里，这常常就是策略模式最合适的样子。
- 如果每条规则不只是一个计算，而是带着好几个相关操作或自己的配置：**用类**，这时经典的策略模式才真正划算。

## 不同的变化，指向不同的方案

同一个停车场程序，换一种变化，候选方案就完全不同：

| 你观察到的变化 | 候选方案 | 先试试的 Python 写法 |
|---|---|---|
| 规则或算法的种类在增加 | 策略（17） | 字典里放函数、直接传函数 |
| 要创建哪种对象，取决于具体情境 | 工厂方法（05） | 一个返回对象的函数 |
| 要接入一个接口不一样的已有组件，比如新的支付终端 | 适配器（10） | 一个转换参数的小函数 |
| 车辆出场后，财务、空位显示屏、会员积分都要知道 | 观察者（18） | 一个回调函数列表 |
| 车位的可用、预约、占用、维修状态下，允许的操作不同 | 状态（20） | 先用一个清晰的状态字段和集中判断 |
| 想在不改原代码的情况下给收费加上日志、缓存 | 装饰器（13）、代理（16） | Python 函数装饰器 |
| 一次收费操作要能排队、记录、撤销 | 命令（19） | 把操作参数存成数据 |

“先试试的 Python 写法”那一列很重要。很多时候，它就已经够用了。只有当它开始别扭，比如字典里要放的东西越来越多，回调之间开始互相依赖，才需要经典模式提供的更完整的结构。

## 一份选择清单

面对一个具体的改动需求，可以按这个顺序问自己：

1. **变化是什么？** 用一句话说出“什么在变、什么不变”。
2. **有证据吗？** 这个变化已经发生，或者有明确的计划；还是只是“将来可能”？
3. **最简单的写法够不够？** 加一个分支、提取一个函数、把规则写成数据，能不能解决？
4. **如果不够，困难具体在哪？** 能指到具体代码，最好能写出一个会失败的测试。
5. **候选方案把变化放到了哪里？** 新增一种情况时，要改几处？谁来改？
6. **代价是什么？** 多了几个类、几层间接调用？读代码的人要多理解什么？测试要多写什么？
7. **将来如果需求没有来，这个抽象能不能轻松撤回？**

最后一条常被忽略。设计是可以撤回的：如果当初为“将来会有很多规则”准备的抽象，两年后发现只用到了两种，把它改回 `if` 也是一次好的重构。

## 小结

- 范式、设计模式、Python 惯用法、架构是不同层次的东西，不要混为一谈。
- GoF 23 种模式分为创建型、结构型、行为型三类；它们诞生于 C++ 和 Smalltalk 的语境，在 Python 里很多可以写得更轻。
- 选择方案时，先说清变化，再找证据，然后比较“直接写法、Python 简化写法、经典模式”三者的代价。
- 引入模式往往不会让“选择”消失，只是把它挪到一个更合适的位置；要看清它挪到了哪里。
- 设计可以撤回。为没有发生的需求准备的抽象，也是一种负担。

## 练习

停车场又来了一个需求：会员可以按月付费，月卡车辆每次停车都免费，但要记录停车次数，月底生成报告。

1. 这个变化属于上面哪一类？它影响的是“收费规则”，还是别的东西？
2. 用“字典里放函数”能不能实现？用“每种规则一个类”呢？哪一种更自然？
3. 有人建议把“月卡”也做成一种车型，放进 `RATES`。你觉得这个建模合适吗？

**思路提示**：月卡不是一种车型，而是车主的一种**身份**，它和车型是两个独立的维度：一辆货车也可以办月卡。把它塞进车型字典，会把两个独立的变化搅在一起。更合适的做法可能是：先判断是否月卡，是则记一次、收 0 元；否则再按车型计费。“记录次数、月底出报告”带有状态，适合放进一个小类。这个变化暂时用不上任何 GoF 模式，但当“身份”和“车型”两个维度都在增长时，可以回头看看第 11 章“桥接”讨论的那类问题。
