# 第 34 章　回顾：能解释自己为什么这样写

> 本章要回答：同一个需求有两种都能工作的设计时，怎样判断它们的复杂度和收益？如果未来的需求不同，结论会不会改变？

全书的最后一章，不再引入新的模式。我们把[第 33 章](33-selective-refactoring.md)的导入工具用另一种合理的设计再写一遍，让两种设计通过同一组测试，然后比较它们。目标不是选出“正确答案”，而是练习本书一直在练的那件事：**说清楚为什么这样写。**

## 两种设计

**设计 A**（[第 33 章](33-selective-refactoring.md)）：函数和数据。

- 每种格式一个读取函数，登记在 `READERS` 字典里；
- 校验规则是函数列表 `RULES`；
- 输出是实现了 `write` 的对象列表；
- 一个 `import_file` 函数把它们串起来。

**设计 B**（本章）：用[第 21 章](../part-04/21-template-method.md)的模板方法。父类 `Importer` 固定“读取 → 校验 → 输出”的流程，每种格式一个子类，只提供“读取”这一步：

```python
class Importer(ABC):
    def run(self, path: Path, sinks: list[Sink]) -> Result:
        """模板方法：流程固定。"""
        rows = self.rows(path.read_text(encoding="utf-8-sig"))
        result = validate(rows, [*RULES, *self.extra_rules()])
        for sink in sinks:
            sink.write(result)
        return result

    @abstractmethod
    def rows(self, text: str) -> list[tuple[str, RawRow]]:
        """每种格式必须提供：把文件内容变成统一的行。"""

    def extra_rules(self) -> list:
        """钩子：某种格式特有的校验规则，默认没有。"""
        return []
```

```python
class CsvImporter(Importer):
    def rows(self, text: str) -> list[tuple[str, RawRow]]:
        return read_csv_rows(text)
```

两种设计对两个示例文件给出完全相同的结果，对不支持的文件类型抛出同样的错误（测试 `test_same_results_for_every_sample` 和 `test_same_errors_for_unsupported_files`）。**从外部看，它们没有区别。** 区别在于它们怎样应对变化，以及读代码的人要理解什么。

## 先比较现在

| | 设计 A：函数和数据 | 设计 B：模板方法 |
|---|---|---|
| 要理解的概念 | 字典、函数列表、一个 `Protocol` | 抽象基类、继承、钩子，外加 A 的全部 |
| 流程在哪里 | `import_file` 里几行 | `Importer.run`，子类不可见 |
| 新增一种格式 | 写一个函数，登记进字典 | 写一个子类，登记进字典 |
| 某种格式特有的规则 | 调用时传入额外的规则 | 子类覆盖 `extra_rules` 钩子 |
| 测试一个读取函数 | 直接调用函数 | 创建子类实例，或者直接测它调用的函数 |

对**现在**的需求（两种格式，规则对所有格式都一样），两种设计的代价相差不大，设计 A 少一层继承，略简单一些。设计 B 的子类其实只是把一个函数包了一层，`CsvImporter.rows` 就是 `read_csv_rows`。按[第 31 章](../part-05/31-simple-versus-pattern-code.md)的说法，这时设计 B 多出来的结构还没有换来对应的收益。

## 再比较未来

真正的区别在于未来。下面设想几种可能的变化，看看两种设计各自怎样应对。

### 情况一：某家供应商有特殊规则

云岭茶业要求商品名里必须写明克重（比如“200g”），这条规则只针对他们。

设计 B 的应对很自然：写一个子类，覆盖钩子：

```python
class YunlingImporter(JsonImporter):
    def extra_rules(self) -> list:
        return [has_weight]
```

设计 A 也能做到：调用 `validate(rows, [*RULES, has_weight])`。两者的结果完全相同（测试 `test_supplier_specific_rule_in_both_designs`）。区别在于“这条规则属于云岭茶业”这个知识**放在哪里**：设计 B 把它放进了一个有名字的类里；设计 A 要在调用的地方（或者另一个“供应商 → 额外规则”的字典里）记住它。

如果这样的特殊要求只有一两家，两种都可以。如果每家供应商都有自己的一套读取细节、额外规则、甚至不同的报告格式，设计 B 的“每家供应商一个子类，所有特殊之处集中在里面”会越来越有优势。这正是模板方法擅长的情况：**流程相同，好几个步骤都因对象而异。**

### 情况二：规则由运营人员配置

店主希望运营同事可以在后台勾选“这周启用哪些校验规则”，不用找程序员。

设计 A 的规则本来就是一个列表，从配置里读出规则的名字，查表得到函数，组成列表，交给 `validate`，几乎不用改结构。设计 B 的规则一部分在全局的 `RULES` 里，一部分在子类的钩子里，“哪些规则生效”分散在类层次中，要支持配置，就得把钩子也改成从配置读取，类层次反而成了障碍。

这时**设计 A 明显更合适**。如果配置进一步复杂到“规则之间可以用且、或组合”，那就到了[第 27 章](../part-04/27-interpreter.md)的规则语言。

### 情况三：文件变得很大

某家大供应商的价目表有两百万行。

两种设计都把整个文件读进内存，都把所有行放进一个列表。两者都要改：读取函数改成生成器（[第 23 章](../part-04/23-iterator.md)），`validate` 边读边处理，输出也要支持分批写入。**这个变化和设计 A、B 的选择无关**，它影响的是另一个维度：数据是一次性处理，还是流式处理。

这一点值得注意：不是所有的变化都能被“选对设计”预先吸收。有些变化会穿过任何一种设计，要求你重新思考数据的流动方式。

### 情况四：什么都没有变

半年过去了，还是这两家供应商，还是这几条规则。

那么设计 A 的简单就是纯粹的收益，设计 B 的类层次就是纯粹的成本：每个新加入的同事都要先理解 `Importer` 的模板方法和钩子，才能看懂导入的流程。

## 怎样做出判断

把上面的分析归纳一下，判断依赖于几个具体的问题：

1. **变化最可能来自哪个方向？** 更多格式、每种格式各有特殊之处，有利于设计 B；规则需要灵活组合、可以配置，有利于设计 A；数据量变大，两者都要改。
2. **有证据吗？** 店主说“下个月还要接三家供应商，每家要求都不一样”，这是证据；“将来可能会有”，不是。
3. **读代码的人是谁？** 团队熟悉面向对象的继承体系，还是更习惯函数和数据？代码最终是给人读的。
4. **撤回的代价多大？** 设计 A 要改成设计 B，只需要把已有的函数包进子类；反过来，把类层次拆回函数，也不困难。两者之间的转换成本都不高，所以**现在选更简单的那个，等证据出现再调整**，风险很小。

对本书的这个小工具，按目前的需求和证据，**设计 A 是更合适的选择**。如果店主带来了情况一的证据，迁移到设计 B 是一次小而安全的重构，而第 32、33、34 章的测试会保证它没有改坏任何东西。

## 全书回顾

回头看这个导入工具的三个版本，几乎每一种做法都在前面的章节里出现过：

- 第一版用 `Decimal` 处理金额、用 `utf-8-sig` 处理 BOM：[第 01 章](../part-01/01-data-and-processing.md)“先想清楚数据”；
- 读取函数是边界上的转换：[第 10 章](../part-03/10-adapter.md)的适配器思想；
- `READERS` 字典：[第 05 章](../part-02/05-factory-method.md)的简单工厂，用[第 28 章](../part-05/28-functions-as-design-tools.md)的字典分派来写；
- 规则函数列表：[第 17 章](../part-04/17-strategy.md)的策略；规则必须互相独立，[第 31 章](../part-05/31-simple-versus-pattern-code.md)说明了原因；
- 输出的 `Sink` 协议：[第 29 章](../part-05/29-types-and-interfaces.md)的 `Protocol`；
- 数据库连接的 `closing`：[第 30 章](../part-05/30-decorators-context-managers-generators.md)的上下文管理器；
- 设计 B：[第 21 章](../part-04/21-template-method.md)的模板方法。

而 23 种 GoF 模式中的大多数，在这个工具里都没有出现。这不是缺陷。本书从第一章起就在说：**模式是对具体困难的回应。** 没有遇到那种困难，就不需要那个模式。能指出“这里用了策略，因为规则互相独立而且在增加”，和能指出“这里没有用抽象工厂，因为没有需要成套切换的家族”，是同一种能力。

## 小结

- 两种都能通过测试的设计，区别在于它们怎样应对变化，以及读代码的人要理解什么。
- 比较设计时，逐一设想可能的变化：哪种设计能吸收它，哪种会被它拖累，哪些变化与设计的选择无关。
- 判断依赖于变化的方向、有没有证据、团队的习惯，以及撤回的代价。当两种设计之间的迁移成本很低时，先选更简单的，等证据出现再调整。
- 能解释“为什么用”和“为什么没用”，比记住模式的名字更重要。

## 练习

回到你自己正在写或者维护的一段代码，选一处你觉得“设计得不太好”或者“用了某个模式”的地方：

1. 用一句话写出它要应对的变化：什么在变，什么不变？
2. 这个变化有证据吗？过去半年，它实际变过几次？
3. 写出另一种可行的设计（更简单的，或者更有结构的），按本章的方法设想三种未来的变化，比较两种设计各自的代价。
4. 你的结论是什么？如果要改，需要哪些测试先保护住现在的行为？

**思路提示**：这道题没有标准答案，它是对全书方法的一次练习。很多时候，你会发现“设计得不太好”的代码，其实是在没有证据的情况下预先做了抽象，或者在变化已经反复出现之后，还停留在一长串复制粘贴里。前一种情况，常见的改进是删掉用不到的扩展点；后一种情况，常见的改进是找出真正在变的部分，把它放到一个可以替换的位置。无论哪种，**先写测试，再动手**。
